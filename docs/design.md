# 架构设计

维护日期：2026-10-26

本文说明项目的设计目标、总体架构、核心机制与扩展边界，作为开发和维护的设计依据。内容描述当前实现；尚未提供的能力单独列在第 10 节。

具体接口与使用示例见 [框架使用指南](framework.md)，构建、配置和安装操作见 [构建与部署](deployment.md)，开发约定见 [AGENTS.md](../AGENTS.md)。

## 1. 项目定位与设计目标

本框架是面向 DeepStream 应用与配套服务的基础框架，以模板仓库的形式使用。产品项目在独立目录中实现拓扑、业务逻辑、模型与插件，框架提供建图、生命周期、元数据采集、消息发布、录像及部署机制。

框架以支持任意 DeepStream 应用为扩展目标，不将某一种视频处理流程定义为唯一入口。示例应用展示多路视频输入、推理、跟踪、消息、录像和 RTSP 输出的组合方式；示例的模型、输出组合和业务规则不构成框架约束。

设计目标如下：

- **适应不同拓扑**：支持应用组合多源、批处理、多级推理、合流与分流，也允许直接使用没有专用封装的 GStreamer/DeepStream 插件。
- **降低应用接入成本**：应用专注配置、拓扑与业务处理，复用入口、生命周期、诊断、就绪和部署约定。
- **支持分层开发**：配置、拓扑、消息及部署逻辑可在没有 DeepStream SDK 的开发机上测试，SDK 适配与真实媒体处理在相应环境验证。
- **明确运行边界**：线程职责、队列容量、停止时限、录像完成条件与消息投递语义均有显式契约。
- **支持独立交付**：运行环境、程序载荷、配置、模型和持久数据分离，应用变更与现场参数变更分别管理。
- **保持长期可维护性**：框架与产品目录分离，公共机制不引用具体产品名称，便于派生项目同步框架更新。

## 2. 核心原则与总体架构

### 2.1 设计原则

| 原则 | 约束与作用 |
|---|---|
| 机制与策略分离 | 框架提供通用机制；源数量、拓扑、事件规则、消息内容和数据保留策略由应用决定 |
| 不预设数量与拓扑 | 单源是多源配置的特例，框架不绑定固定模型数量或输出组合 |
| 保留底层能力 | 块提供默认值与属性透传，图模型可直接添加插件；应用可以使用原生建图入口 |
| 扩展以独立单元接入 | 应用、服务、插件和模型通过目录及公共约定接入；缺少通用扩展点时先补机制 |
| 依赖分层、按需链接 | SDK 相关类型留在 SDK 目标中，普通配置与拓扑代码不要求 SDK |
| 契约可验证 | 配置、图、消息、载荷与安装规则通过测试、预检或运行期检查验证 |
| 部署与业务解耦 | 部署工具依赖统一入口、挂载点、服务标签和就绪信号，不识别具体业务代码 |
| 框架可升级 | 产品通过公共接口扩展；不同需求优先用可选项表达，不改变公共接口的默认语义 |

### 2.2 职责边界

| 层次 | 负责内容 | 主要位置 |
|---|---|---|
| 产品策略 | 配置字段、视频拓扑、业务事件、消费与上传逻辑 | `services/` |
| 产品资产与平台选择 | 推理解析插件、模型、部署平台及参数覆盖 | `plugins/`、`models/`、`profiles/` |
| 应用运行机制 | 配置、建图、生命周期、元数据、发布器、录像与服务运行时 | `framework/cpp/`、`framework/python/` |
| 构建与交付机制 | SDK 探测、目标登记、镜像、载荷、渲染、打包与安装 | `framework/cmake/`、`framework/docker/`、`framework/deploy/` |

框架不包含具体产品名称，也不反向依赖产品代码。示例应用与其他应用使用同一套公共接口，不享有特殊接入路径。

### 2.3 术语

| 术语 | 含义 |
|---|---|
| 服务单元 | `services/<name>/` 中的代码、配置模板和 Compose 片段，可包含一个或多个 Compose 服务 |
| 块（Block） | 向图中添加可复用子图的构造函数；通常由配置结构与 `Add*` 函数组成 |
| 组件（Component） | 参与管线生命周期的运行期对象，例如元数据探针、录像器、心跳和统计组件 |
| 图（Graph） | 元件、属性、连接及 pad 端点的结构化描述，实例化前不创建实际媒体管线 |
| 载荷 | 安装到 `/workspace` 的程序、插件、Python 包和资源，由 apps 镜像向卷播种 |
| 部署方案（profile） | 平台相关的构建变量、Compose 服务覆盖和应用配置覆盖 |

### 3.2 C++ 模块

C++ 代码使用 C++17，命名空间为 `dsf`。主要构建目标与公共依赖如下，完整依赖声明以 `framework/CMakeLists.txt` 为准。

| 目标 | 职责 | 公共依赖 |
|---|---|---|
| `dsf_config` | 严格 YAML 读取、约束与配置摘要 | 无；yaml-cpp 为实现依赖 |
| `dsf_gst` | 插件内省、图模型、管线运行与组件接口 | `dsf_config`、GStreamer |
| `dsf_ds` | DeepStream 块、纯数据模型与消息编码 | `dsf_gst`、nlohmann-json |
| `dsf_publish` | 发布接口与 Redis Stream 实现 | `dsf_config`；hiredis 为实现依赖 |
| `dsf_record` | 分段录像、命名、完成事件与收尾 | `dsf_ds` |
| `dsf_app` | 应用入口、装配、日志、就绪与统计 | `dsf_gst`、`dsf_publish`、日志依赖 |
| `dsf_ds_meta` | DeepStream 元数据采集与转换 | `dsf_ds`、DeepStream SDK |

`dsf::framework` 聚合不需要 SDK 的框架目标；`dsf::ds_meta` 仅在 SDK 可用时创建。配置和发布接口不暴露 yaml-cpp、hiredis 类型；DeepStream SDK 类型只出现在 SDK 适配接口及相关目标中。

DeepStream 块通过工厂名和属性名描述插件，因此构造图本身不要求 SDK 或 GPU。应用应将配置读取与拓扑生成放在独立的普通库中，将 SDK 元数据接入放在应用可执行文件中。

SDK 探测使用头文件、库和真实编译链接探针。开发构建在 SDK 不可用时跳过相关目标；发布构建要求 `DSF_REQUIRE_DEEPSTREAM=ON`，SDK 不可用即失败，避免生成缺少应用的载荷。

## 4. 配置、图模型与插件能力

### 4.1 配置读取即声明

配置读取代码同时定义字段、类型、默认值和约束。`Reader` 记录访问路径，`Finish()` 拒绝未读取的键，使字段拼写错误和无效配置在启动前暴露。

读取器支持标量、映射、列表和插件属性映射，拒绝重复键、带点号的键、错误类型及非有限浮点值；null 按缺失值处理。字段约束随读取声明，跨字段规则由应用执行，错误包含文件与完整配置路径。

`Secret` 标记敏感字段，配置摘要对其打码。插件属性使用 `Props` 读取自由映射，具体取值是否被插件接受留给能力检查。模板与读取代码的一致性可通过 `Document::LeafPaths()` 和 `Reader::DeclaredPaths()` 对照验证。

这种设计将字段定义集中在使用它的代码中；应用无需维护另一套与读取逻辑平行的 schema。Python 服务遵循相同的严格读取原则，使用 `dsf.config.Reader`。

### 4.2 结构化图模型

`Graph` 保存元件工厂、名称、属性、敏感标记及连接端点。同一份数据用于三个阶段：

| 阶段 | 行为 |
|---|---|
| 诊断 | `Describe()` 输出管线描述，对敏感属性打码 |
| 能力检查 | `Requirements()` 推导实际使用的工厂、属性与取值需求 |
| 运行 | `Instantiate()` 原生创建元件并连接，失败时释放已创建的对象 |

连接支持静态 pad、request pad 和 sometimes pad 的延迟连接。`Tee` 与 `Branch` 用于分支，`Branch` 自动插入 queue，使不同分支拥有独立的流线程。

图模型使运行拓扑、能力清单和诊断输出来自同一份定义。应用也可通过 `Pipeline(name, builder)` 接入自定义原生建图，或用 `Pipeline::Launch` 创建文本管线建图器；此时图之外的能力需求和生命周期责任由调用方明确管理。

### 4.3 属性透传与能力内省

块先设置默认值，再通过 `Element::Apply` 应用配置中的 `properties:`。透传可覆盖同名属性或增加属性，配置路径随属性保存，以便诊断定位。

能力检查依据运行环境中的插件元数据，验证工厂、属性、枚举和组件所需信号。属性按 `GParamSpec` 转换与校验，不通过 DeepStream 版本号推断能力。

检查分为两层：

- `--check-config` 读取配置、校验业务约束并生成图，不实例化管线或主动检查插件，适用于离线安装预检。
- `--check-config --plugins` 在具备插件运行条件的环境中进一步检查能力。正常运行也必须通过能力检查。

属性透传不消除插件本身的限制。当前 `AddMux` 默认设置 `width`、`height` 等属性；对于不支持这些属性的 nvstreammux 实现，应用需按其契约直接组图或提供适配块。框架不承诺不同插件实现之间自动转换配置。

### 4.4 DeepStream 块

块采用配置结构与构造函数组合，负责局部子图和默认参数，应用负责组合顺序。当前提供源、mux、推理、跟踪、analytics、preprocess、元数据挂载点、OSD、tiler、demux、编码、RTSP 输出及分段录像等构造能力。

源块支持 RTSP、文件、通用 URI、V4L2 和测试源，输出规范为 NVMM NV12。`rtsp`、`file`、`uri` 使用 nvurisrcbin，默认设置 `num-extra-surfaces=8`，为下游持有解码 surface 留出余量；队列只改变缓存与调度，不能替代解码 surface 容量。需要更多余量时由应用通过属性调整。

推理块可选择 nvinfer 或 nvinferserver，多级推理由应用按顺序组装，并通过插件配置和属性指定级联关系。编码器的平台差异通过属性表达。RTSP 输出默认使用 TCP，并允许覆盖传输属性。

没有专用块的插件可以通过 `Graph::Add` 接入；专用块不构成框架支持插件的封闭列表。

## 5. 生命周期、线程模型与停止收尾

### 5.1 管线与组件

`Pipeline` 是一次性运行对象，`Run()` 在调用线程运行主循环。`Assembly` 持有应用登记的组件与发布器，生命周期覆盖管线运行。

| 扩展点 | 契约 |
|---|---|
| `Require` | 声明图之外的能力需求 |
| `OnCreated` | 建图后、进入 PLAYING 前，按登记顺序取得元件、挂探针和连信号 |
| `OnPlaying` | 真正进入 PLAYING 后调用一次；异步切换状态的 sink 可能等待首帧 |
| `OnMessage` | 在控制线程处理总线消息 |
| `OnStopping` | 首次停止请求后、注入 EOS 前调用；自然 EOS 和错误不保证经过此回调 |
| `Drained` | 排空期间报告组件是否完成收尾 |
| `OnReleased` | 管线置 NULL、流线程停止后按逆序清理；即使创建阶段失败也会调用 |
| `Healthy` | 运行结束后判断组件是否成功完成；失败使应用返回失败退出码 |
| `Report` | 提供周期统计 |

组件构造函数不得创建业务文件、访问设备或连接网络，因为配置预检也会构造组件。生命周期回调的异常由框架隔离，一个组件失败不阻止其他组件清理。

### 5.2 线程职责

控制线程处理总线、生命周期、定时任务和停止流程；媒体线程上的探针及信号回调只进行必要的数据复制、轻量标记与入队；网络投递在后台线程完成。媒体线程不得等待网络，也不得持有控制线程停止时需要等待的资源。

`Post` 将动作排队到控制线程执行，`Every` 管理周期任务，`RequestStop` 可由任意线程调用。管线结束时清理其定时任务和未执行动作，避免回调访问已经释放的对象。

主循环默认使用 GLib 默认上下文，以驱动通过默认上下文注册内部定时器的插件，例如 nvurisrcbin 的 RTSP 重连。多条管线并行时可为次要管线设置 `Options::private_context`；依赖默认上下文的插件定时器仍需由默认上下文驱动。

### 5.3 启动、排空与结果

启动时限约束的是 GStreamer 状态切换，不代表输入一定会持续供帧。异步切换状态的 sink 可能等待首帧完成 preroll，使按需产帧的管线长时间无法进入 PLAYING；是否等待取决于元件及其配置，并非所有 live 管线都必须等待首帧。时限为正数时，管线必须在时限内进入 PLAYING；为 0 时禁用启动超时，状态切换返回失败或总线报告错误时仍按启动失败或运行失败结束，等待期间的停止请求照常排空。首次停止请求触发组件 `OnStopping`，随后注入 EOS 并进入有界排空；排空期间再次收到停止信号、请求立即停止或超过时限时强制结束。运行期的总线错误默认立即结束；应用设置 `drain_on_error` 后先排空再以运行失败结束，使其余分支（例如录像）完成收尾。

启动计时在 `set_state(PLAYING)` 返回异步状态切换结果后开始，不覆盖同步建图、组件初始化或 `set_state` 内部阻塞。启动超时、心跳和统计定时器均由控制主循环驱动，不能中断控制线程中的阻塞调用。

结构化图通过 `DrainPoints()` 找到源之后的注入点，使 EOS 能进入下游处理链，避免带重连逻辑的源将 EOS 作为断流消化。自定义建图没有这些注入点时，框架向整条管线发送 EOS。

排空满足任一条件即可结束：收到管线 EOS；或者 EOS 已到达全部 sink 输入，且所有组件报告 `Drained()`。后者避免网络 sink 等待远端会话关闭而阻止退出，同时允许录像组件等待文件封装完成。

默认启动时限为 30 秒，排空时限为 5 秒，可由应用调整，启动时限为负数时视为启动失败；排空时限必须小于容器停止宽限期。结果区分自然 EOS、正常停止、强制结束、建图失败、启动失败、运行失败和启动超时，组件健康状态参与最终退出码判断。

### 5.4 就绪与统计

标准组件 `ReadinessHeartbeat` 更新 `$DSF_READY_FILE`，默认路径为 `/tmp/dsf.ready`；`StatsReporter` 汇总组件与发布通道统计。Compose 健康检查判断就绪文件是否在规定时间内更新。

DeepStream 应用通过 `ReadyWhen` 使用 `MetaTap::frames()`，按批次元数据中的真实帧数判断处理是否推进；普通管线可按指定元件的 buffer 数计数。心跳和统计组件在 `OnCreated` 注册定时器，由主循环按各自周期调度，不等待 PLAYING；组件的 `Report()` 须能在进入 PLAYING 前报告统计。

就绪默认表示应用活着（`readiness.require_input: false`）：心跳每次调度都更新就绪文件，计数不增长也一样。原因是“没有输入”并不总是故障：线阵相机、外触发相机在启动后可能长时间不产帧，若就绪要求输入，这类应用会一直不健康，安装器的就绪等待也只能超时失败。输入是否在供帧交给看门狗与就绪文件中的计数和空闲时长；需要让健康状态直接反映输入的应用设 `require_input: true`，此时心跳只在计数增长时更新。

可选的 `watchdog.stall_timeout_s` 让同一计数兼作看门狗：超时不增长时排空停止并以失败退出，交给容器的重启策略。Docker 不会重启 unhealthy 的容器，健康检查本身只能暴露问题，不能恢复。

要求输入时，就绪表示所选进度指标在推进。总帧数增长不能证明每一路输入都正常，主循环推进也不能证明 Redis 等外部依赖健康；需要逐源或业务级健康判断时由应用提供相应监测。

## 6. 多源、元数据、消息与录像

### 6.1 多源与标识

应用为每个源配置唯一且可用于路径的 `id`，通过 `SourceRegistry` 建立 mux pad 索引与业务源标识之间的映射。应用负责使注册顺序与实际连接一致，元数据由帧的 `pad_index` 查找 `source_id`。

多路源可在 mux 后共享推理和跟踪，再通过 tiler 拼接输出或 demux 按源拆分。推理前的 raw 录像从每路源规范化输出处分支，推理后的录像由应用选择按源或合流组织。

框架提供这些组合机制，但不要求所有源启用同一种输出。当前公共接口围绕启动前组图设计，不提供运行期增删源的完整管理接口。

### 6.2 元数据采集与扩展

元数据模型为 `BatchRecord → FrameRecord → ObjectRecord`，不含 SDK 指针，可在复制后跨线程传递。帧记录包含源标识、帧号、媒体时间戳、墙钟时间、尺寸和目标；目标记录包含类别、置信度、边界框、可选跟踪 ID、分类结果和扩展属性。

`MetaTap` 位于 SDK 适配层，在命名挂载点的 src pad 读取 `NvDsBatchMeta`，转换为纯数据记录。边界框使用 mux 输出坐标空间，采集器的尺寸配置应与实际图一致。

默认采集包含检测与分类结果；analytics 由选项启用。`AddFrameExtractor` 和 `AddObjectExtractor` 允许应用将 SDK 自定义元数据转换为记录中的 `extra`。

采集点可选地把选中的帧整帧编码为 JPEG，放入帧记录。编码使用 SDK 的批量编码库直接读取 GPU 上的批次 surface，Jetson 上由 NVJPG 硬件完成，dGPU 上由 nvJPEG（CUDA）完成，避免把整帧拷回主机内存；图片与元数据来自同一个 buffer，天然对应同一帧。编码在采集点的流线程中同步等待完成，`AddMetaTap` 在启用编码时插入 queue，使编码与上游推理处于不同的流线程。帧选择规则（默认有目标的帧）由应用决定。编码结果以 user meta 形式挂到帧上，复制后立即移除，不随批次流向下游。

`OnBatch` 在媒体线程同步执行，适合计数、录像标记和快速入队；`OnBatchAsync` 使用有界队列交给工作线程，队列满时丢弃并计数。异步处理不延长 SDK 元数据对象的生命周期。

### 6.3 消息与投递

消息编码与发布接口分离。框架提供 schema v1 的检测消息和录像事件编码器，也允许应用使用自己的消息结构。

内置消息以 `schema_version`、`event_type`、`source_id`、`timestamp_ms` 为公共字段。检测消息在编码时处理边界框裁剪、取整和无效面积过滤；录像完成消息中的 `end_ms` 为 `start_ms`（分段第一帧进入录像器时的主机墙钟）加分段内画面的时长，不含断流。字段约定见 [框架使用指南](framework.md)。

`Publisher` 管理连接和运行生命周期，`Channel` 提供非等待网络的 `TryPublish`。Redis Stream 实现使用一个连接、一个工作线程和多个独立有界队列，避免检测消息占用录像事件的队列容量。消息入队后立即唤醒工作线程发送，不等待凑批；积压时每轮最多取 `batch_size` 条、`batch_bytes` 字节，以 pipelining 合并发送 `XADD`，减少往返次数，同时避免大消息使 Redis 单线程长时间阻塞。发送时按配置进行近似长度裁剪。

一条消息由若干字段组成，字段值二进制安全。检测消息的图片作为同一条记录的 `image` 字段原样发送，`payload` 中只有图片描述；不做 base64，也不另开 Stream，消费端从一条记录同时得到检测结果和对应画面。图片使消息达到数百 KB，因此通道可以设置积压字节上限，Redis 应部署在本机，Stream 长度只按抖动缓冲设置（例如 100 条）。存盘、上传等证据处理由消费服务完成，应用不写图片文件。

选用 Redis Stream 而非 Pub/Sub，是因为消费端离线或处理变慢时消息仍保留在 Stream 中，可通过消费组分担处理并确认进度；Pub/Sub 在无订阅者时直接丢弃消息。消费端应使用阻塞读取（`XREAD`/`XREADGROUP` 的 `BLOCK`），新消息写入后即被唤醒，不应采用定时轮询。

默认投递语义为**内存队列、至多一次**。队列满、发送失败或停止排空超时可能丢失消息，失败计入统计；不落盘，不重试已提交发送的消息。连接不可用时尝试重连，尚未取出的消息受队列容量约束。

发布器在管线之前启动，在管线及组件收尾之后停止，为最后一个录像完成事件保留投递机会。持久化、确认、补发或其他后端由自定义 `Publisher` 实现，业务也可直接在图内接入消息插件。

### 6.4 分段录像

分段录像由 `AddSegmentSink` 与 `SegmentRecorder` 组合实现，每个录像器对应一个 splitmuxsink 和一个源分支。框架负责分段切分、命名、临时文件、完成判定及事件回调，应用决定何时录像和如何处理事件。

文件布局为：

```text
<root>/<source_id>/<branch>/<source_id>-<branch>-<起始本地时间>-<序号>[-detected].mp4
```

`branch` 是应用定义的录像分支名，用于区分同一路源上的多路录像，例如示例应用中推理前原始画面的 `raw` 和叠加检测框后的 `osd`；框架只要求它是合法路径段。

起始本地时间形如 `20261005T163012.345`，为本地日期时间与毫秒，不带时区标记。时区取自容器挂载的 `/etc/localtime`，便于现场直接按文件名定位时间段。文件名中的时间只供人阅读：实行夏令时的时区在回拨时同一本地时刻会出现两次，跨时区读取也无法从文件名还原绝对时间。文件名不含冒号，序号保证同一时刻或时钟回拨时不覆盖旧文件。程序应以录像事件中的 `start_ms` 与 `path` 为准，不解析文件名。`start_ms` 与文件名中的时间取分段第一帧进入录像器的时刻：splitmuxsink 要收齐一个 GOP 才打开新文件，打开时的墙钟晚一个关键帧间隔，因此录像器在请求切分时记下这一帧的墙钟，打开文件时按第一帧的 running-time 取用。

已知并接受的偏差：源上线后的第一个分段，第一帧带着管线与编码器预热的额外延时进入录像器，`start_ms` 因此偏晚，按画面时长算出的 `end_ms` 与下一分段的 `start_ms` 重叠约一个启动延时（本机实测 0.3–0.4 秒）；之后的分段按稳态延时计时，相互衔接。这一偏差无法在打开文件时修正：splitmuxsink 打开第一个文件时只收到了第一帧（之后的文件要收齐一个 GOP 才打开），没有后续帧可以估计稳态延时，而 `recording_started` 与文件名都在此刻确定。可行的修正都要改变契约——收尾时改写 `start_ms` 会使 started 与 finished 两个事件的 `start_ms` 不一致、文件名中的时间不再对应；按最后一帧的到达时刻计算 `end_ms` 会使首段的 `end_ms - start_ms` 不等于 `duration_ms`。在出现需要按墙钟把检测与录像对齐到半秒以内的消费者之前不做修改；`tools/record_gap_check.py` 把不超过 1 秒的重叠报告为 WARN。

写入时使用 `.mp4.tmp`；只有收到 `splitmuxsink-fragment-closed` 且改名成功后，才触发完成回调。启动时清理本源本分支遗留的临时文件。`MarkDetected()` 可从任意线程为当前分段标记检测结果；是否出现过目标在收尾时才确定，因此只体现在最终文件名的 `-detected` 后缀上，分段 id 不变。

正常停止时，EOS 随数据流经过编码器和队列后到达录像入口，使已在途的帧先完成写入。录像器不会在 `OnStopping` 中立即封装文件；若收尾在 `eos_fallback` 时限内仍未完成，则向录像入口发送 EOS 兜底，封装已经接收的帧。默认兜底时限为 3 秒，应小于管线排空时限。录像入口没有收到任何帧时，录像器丢弃到达 splitmuxsink 之前的 EOS（GStreamer 1.20 的 splitmuxsink 无数据收到 EOS 会终止进程），排空不受影响。

分段时长按画面计时而不按时间戳计时。splitmuxsink 的 `max-size-time` 以时间戳之差判断是否放得下下一个 GOP，断流前最后一个 GOP 的"时长"延伸到恢复后的第一个关键帧，包含整个断流，于是在它之前提前切分，留下一个只有一个 GOP 的小分段，并以恢复时的墙钟命名。录像器已在入口检查每一帧，由它在画面时长达到分段时长后的关键帧处请求 `split-at-running-time`，断流时长自然不计入，切分规则也只有一处。

直播源断流期间 running-time 照常前进，恢复后的第一帧带着整个断流时长的跳变到达。断流留在文件中表现为长时间的静止画面，与真实的静止场景无法区分，对监控录像有误导性；断流前的分段也不应等到恢复才收尾，否则文件在整个断流期间不可读、没有完成事件，进程在此期间异常终止还会丢失这一段。两者由同一个阈值 `split_on_gap` 处理：输入停止超过阈值时收尾当前分段，恢复后的第一帧开始新分段（时间戳跳变超过阈值时同样切分，覆盖断流中没能收尾的情况）。恢复后、第一个关键帧之前的帧不写入录像：它们延续断流前的 GOP，不能作为新分段的开头。为了不丢或少丢，应用在编码器输入上登记 `KeyframeOnGap`，请求恢复后的第一帧编成关键帧；dGPU 的 NVIDIA 编码器只响应自己的 `nv-enc-force-idr` 事件且晚一帧生效，Jetson 的只响应 `force-IDR` 动作信号，三种请求同时发出。两者都在框架中、默认开启并可关闭：切分属于录像器的命名与收尾职责，关键帧请求属于编码器块，RTSP 输出同样受益。

GStreamer 1.20 的 splitmuxsink 只在收到下一个关键帧或 EOS 时写出最后一个 GOP；EOS 之后它不再接收数据，在运行中把它重置为 READY 再启动会发出 async-start，使整条管线在断流期间停在 PAUSED，停止时还会报时间戳错误。录像器因此在断流中请求在最后一帧之后切分，并补入两帧占位关键帧推动 splitmuxsink 按正常流程收尾：断流前的分段完整写出，占位帧单独落在一个临时文件中。splitmuxsink 要到恢复或停止时才关闭这个文件，录像器在它打开后立即删除目录项，目录中不出现占位文件。补帧与恢复的帧经同一个 pad 的流锁串行，恢复的帧先到时占位帧被丢弃，时间戳不会倒退。

录像器提供可选的按数量保留机制：保护最新 `keep_files` 个分段，超过 `max_files` 时先删无目标、再删有目标的旧分段；剩余空间低于 `min_free_bytes` 时可删入保护区，因为写满磁盘会使所有录像失败。清理放在录像器内，是因为录像器拥有目录与命名规则，只删除自己产生的已收尾文件；依赖至多一次的事件或解析文件名的外部服务都不能可靠地完成这件事。各项上限与是否启用由应用决定。

封装、改名或清理删除失败、仍有未关闭分段时，录像器健康状态失败。上传及事件触发策略由独立服务或应用实现。

## 7. 应用入口、Python 服务与扩展

### 7.1 C++ 应用

应用通过 `Describe`、`Load`、`Build` 提供身份信息、配置读取和装配逻辑，由 `dsf::app::Main` 统一处理 CLI、日志、运行流程和退出码。

`Load` 与 `Build` 均须无外部副作用。预检和管线诊断执行这两个步骤，但不会启动发布器或媒体管线；日志目录、业务目录和外部连接在运行阶段创建。

统一入口提供配置检查、插件能力检查、管线诊断、软件自检及版本查询。软件自检运行 30 帧 GStreamer 管线，用于检查载荷基础可运行性，不代表 GPU 推理已验证。退出码约定为 0 成功、1 执行失败、2 用法错误。

### 7.2 Python 服务

`dsf.service.Service` 负责配置入口、日志、信号和就绪文件，应用提供无副作用的配置加载函数及业务主循环。主循环通过 `alive()` 或可被停止信号打断的 `sleep()` 声明进度。

框架 Python 运行时随载荷安装。服务依赖写在本单元的 `requirements.txt`，由构建流程汇总安装到载荷；Redis 消费、上传等具体业务库和处理逻辑由服务引入。

### 7.3 服务单元与示例

服务单元包含 `compose.yaml`，可按需包含源代码、`CMakeLists.txt`、配置模板、依赖清单和测试。应用、插件和 Python 服务分别通过 `dsf_add_app`、`dsf_add_plugin`、`dsf_add_python_service` 登记，安装规则决定交付内容。

`new-app` 根据 C++ 或 Python 模板生成服务目录；`init-project` 设置产品项目身份。新增单元通过目录发现与公共约定接入，平台设置放在 profile 中。

`example-app` 展示多路视频到推理、跟踪、消息、录像和 RTSP 的完整组合：`config.cpp` 负责配置，`plan.cpp` 生成图，`main.cpp` 接入 SDK 元数据、录像器和发布通道。配置与图结构可脱离 SDK 测试。多源 RTSP 输出经 tiler 合流，录像可经 demux 分流；这些是示例策略。

`example-service` 展示读取 Redis 录像事件并记录日志的服务循环，不包含可靠消费、上传或存储清理机制。模型和推理解析库位于产品资产目录，其来源说明和许可证随各自资产维护。

## 8. 构建、载荷与部署设计

### 8.1 镜像与载荷分离

镜像构建与业务运行的关系如下：

```text
DeepStream 上游镜像 → base → builder：编译、CTest、CMake install
                       └→ runtime-check：在 base 中检查已安装载荷
busybox → apps：只包含通过 runtime-check 的载荷，用于卷播种
业务容器：base + 只读载荷卷 + 配置 + 模型 + 可写数据
```

base 固定运行环境和公共依赖，builder 提供工具链及测试依赖。runtime-check 使用 base 环境，以非 root、无网络、限时方式检查应用版本、软件自检、Python 运行时，并执行每个 Python 服务的 `--version`，使未声明的顶层依赖在构建时暴露；项目没有应用或服务时跳过相应检查。apps 最终阶段基于 busybox，仅复制通过检查的载荷。

载荷范围只由 CMake 安装规则决定，Python 依赖按单元清单汇总安装。新增应用无需在 Dockerfile 中单独列出复制路径。

base tag 包含 base Dockerfile、上游镜像与 `BASE_APT_PACKAGES` 的输入摘要，使运行环境输入变化对应新标识；apps 使用项目载荷版本。载荷卷的卷名带载荷内容的摘要：新载荷总是播种到新卷，服务因卷名变化而重建，安装不需要删卷，也不会在旧卷上运行旧程序；开发机的卷名在构建前确定，固定为 dev，卷与镜像不一致时播种失败而不是悄悄沿用。持久数据位于独立挂载中。

### 8.2 服务公共约定

业务服务通过 `framework/compose/defaults.yaml` 的 `dsf-service` 继承公共定义，使用 `${BASE_IMAGE}`，按渲染用户 UID/GID 运行，不设置固定 `container_name`。公共定义包含就绪检查、日志轮转、预检标签和载荷依赖。

| 挂载点 | 内容 | 业务容器权限 |
|---|---|---|
| `/workspace` | 程序载荷 | 只读 |
| `/config` | 渲染后的配置 | 只读 |
| `/models` | 模型与推理配置 | 只读（engine 写在 `/data/engines`） |
| `/data` | 录像与其他持久数据 | 可写 |

公共部署机制通过 `--check-config` 和 `io.deepstream.config-check` 标签执行服务预检，通过 `$DSF_READY_FILE` 判断运行进度。容器 runtime 由需要 GPU 的单元自己声明（公共定义不预设，Python 服务不一定需要 GPU）；设备与补充用户组由 profile 定义。

### 8.3 配置分层与渲染

配置输入分为项目默认值、平台覆盖和现场答案，优先级为：

```text
site-fields.env 中的默认值 < project.env < profile 的 x-build < site.env
```

`site-fields.env` 声明现场字段、默认值、必填与可空规则；`site.env` 保存实际答案（`KEY="值"`，外层一对引号在读取时去掉），不提交、不打包。渲染出的 `.env` 由 Compose 解析，值一律加引号，现场值中的 `$`、`#` 与引号不会被插值或截断。身份、版本、镜像和固定挂载点等保留键不能被现场字段占用。

模板来自 `services/*/templates/<type>/`，渲染到 `generated/<type>/`。未定义的占位符和跨单元同名输出均报错；profile 的 `x-app-<type>` 进行深合并，映射递归合并，列表与标量整体替换。

渲染器先计算并校验完整计划，再替换 `.env` 与 `generated/`。`COMPOSE_FILE` 按根 Compose、构建定义（只在开发机）、名称排序的单元片段、profile 的顺序组装，使配置预检与实际启动使用相同定义。构建定义单独成文件、不进发布包：目标机从不构建，某些 Compose 命令（例如 `run` 一个与构建目标共用镜像的服务）却会在定义存在时尝试构建，而包中没有构建上下文。

profile 用 `x-platform` 声明面向的平台。打包时镜像必须是这个平台，安装时只提供与发布包平台（及 DeepStream 版本）相符的 profile，选错平台在停服前失败，而不是停服后 GPU 服务起不来。

网络模式是平台差异，但必须覆盖全部服务：只要有一个服务留在默认网络，Compose 就会创建 bridge 网络。因此 profile 的 `x-network-mode` 由渲染器展开为覆盖文件，排在 `COMPOSE_FILE` 最后，给所有未显式声明 `network_mode` 的服务设置该值；新增单元不需要修改 profile。host 网络下 Compose 的 DNS 不生效，渲染器同时用 `extra_hosts` 把每个服务名指向回环地址：配置只写服务名，不随网络模式分叉。默认不设置，服务通过 Compose 网络的服务名互相访问。

交互安装把继承值（`project.env` 与所选 profile 的 `x-build`）作为提问默认值。回车接受的值会作为答案写入 `site.env` 并获得最高优先级，所以它必须与渲染时的继承值一致。

### 8.4 模型与 engine

模型目录分为人写的规格（`model.yaml`）、工具写的发布事实（`release.json`）、已发布的产物（`artifacts/`）与 nvinfer 配置。规格中的类别、输入尺寸与输出布局是部署契约：打包前校验它们与发布记录、产物哈希、标签及 nvinfer 配置一致，契约漂移在开发机上失败而不是在现场。训练数据与过程留在仓库外的训练根目录，见 [training.md](training.md)。engine 预构建工具扫描 nvinfer 配置，不依赖具体应用字段；输出路径遵循 `model-engine-file`。

复用指纹包含 ONNX、TensorRT 版本、GPU 计算能力、构建参数及 engine 自身哈希。只有文件非空且指纹匹配时才复用；同一目标使用文件锁串行检查与构建，临时文件成功后才替换正式 engine，失败保留旧文件。

额外构建选项由配置旁的 `.trtexec` 文件提供并计入指纹。engine、指纹和锁文件不进入发布包，在目标 GPU 环境生成。使用 nvinferserver 等其他推理后端时，其模型部署由相应服务管理。

### 8.5 发布包与安装

发布包包含 apps 镜像、依赖镜像、部署文件、模型、发布事实和 SHA-256 清单；base 镜像按发布选项携带。打包时检查镜像平台一致性，排除源码、Dockerfile、现场答案、渲染结果及 engine。

安装分为预检与执行，顺序如下：

1. 核对发布事实、平台、完整性和安装目标路径。
2. 选择 profile，收集或沿用现场答案，检查清洁安装范围与退役文件冲突。
3. 加载镜像，在临时目录渲染配置；按最终 Compose 检查镜像平台与可写挂载，用新载荷离线执行服务预检。
4. 预检全部通过后重验目标，再用已安装定义停止旧服务；启动新服务后清理旧载荷卷。
5. 写入发布文件、受管理清单、现场答案和预检过的配置快照，启动服务并有界等待就绪。

预检失败不得停止旧服务或修改安装目录。`--dry-run` 完成预检后输出计划并结束；预检仍可能加载镜像、准备安装目录之外的数据挂载，但不进入停服和写入安装目录阶段。

普通升级保留现场新增且不冲突的文件；被现场修改过的退役受管理文件在停服前报告冲突。路径检查拒绝危险的目录重叠、符号链接和类型冲突。清洁安装保留独立数据目录与镜像。

安装不是跨文件与容器的事务，停服后的失败不自动回滚；需要恢复时重新安装相应版本的发布包。完整安装规则见 [构建与部署](deployment.md)。

### 8.6 部署工具组织与框架更新

部署工具按环境文件、现场参数、命名、渲染、镜像操作、打包、文件清单和安装阶段拆分。Docker/Compose 调用集中在统一封装中，测试可替换该封装验证流程；部署工具使用标准库，渲染时才导入 PyYAML：开发机上直接渲染；安装器总在 base 镜像中渲染，每个现场使用同一套解释器与库，目标机不需要 PyYAML。

框架版本由 `framework/VERSION` 管理。派生项目通过同步框架目录、入口脚本和对应文档获取更新，产品目录保持独立；配置、接口或部署约定的变化应在升级前通过模板测试、配置预检和目标环境验证确认。

## 9. 测试与验收边界

测试按依赖和验证目标分层：

| 层次 | 验证内容 | 环境 |
|---|---|---|
| 配置与图结构 | 严格读取、模板一致性、图描述、能力推导、块组合与多源标识 | 无 SDK 开发机 |
| 管线与组件 | 生命周期、异常清理、停止排空、软件录像、消息编码与 Redis 投递 | GStreamer 软件插件；部分用例需要 Redis |
| 应用核心与插件解析 | 配置规则、输出拓扑、使用替身 SDK 头编译真实解析源码 | 无 SDK 开发机 |
| 部署工具 | 渲染、打包、安装顺序、路径安全、engine 构建流程和仓库约定 | 假 Docker / 假 trtexec；部分检查使用真实 Docker CLI |
| SDK 构建 | 应用与插件编译链接、CLI 检查 | DeepStream builder |
| 运行环境自检 | 已安装载荷的基础依赖和软件管线 | 原始 base 环境，非 root、无网络 |
| 目标验收 | 真实输入、推理与跟踪、元数据与消息、完整录像、RTSP 输出、engine 复用和权限 | 对应 GPU、驱动、SDK 与 Linux 环境 |

软件录像测试校验停止后最后一段的可读性及帧数，避免将文件存在误判为完整收尾。消息与部署测试验证明确的投递和安装边界，不替代业务系统端到端验收。

开发修改需运行构建和 CTest；SDK、镜像或 GPU 相关变更还需执行编译服务器镜像构建及相应目标验证。缺少软件插件、Redis 或 Docker CLI 时，一些用例会打印 SKIP 后成功退出，应检查实际覆盖范围。

构建成功、软件自检通过或容器健康都不能单独证明真实媒体路径可用。测试矩阵定义应验证的范围，具体发布的验证结论需附对应环境与结果。

## 10. 当前限制与扩展方向

| 方向 | 当前边界与接入方式 |
|---|---|
| 运行期增删源 | 没有完整公共接口；需设计运行期图变更、源注册表同步、pad 释放及元数据生命周期 |
| 消息插件封装 | 没有专用 `MsgBroker` 块；应用可直接组装 nvmsgconv/nvmsgbroker，或实现 `Publisher` |
| 事件触发录像 | 当前提供连续分段录像；Smart Record 需独立 SDK 组件及事件策略 |
| Python 媒体应用 | Python 运行时面向普通服务，未提供 pyds 媒体管线封装 |
| 可靠投递与消费 | 默认发布器不提供持久化、确认与补发；消费进度、去重和可靠性由服务实现 |
| 录像上传与归档 | 录像器只按数量与剩余空间清理本目录的分段（见 6.4）；按时间的保留期、上传与归档由独立服务实现 |
| 声明式拓扑 | 当前以代码组图和配置属性组合，不提供完整 YAML 拓扑语言 |
| 平台覆盖 | 通用机制允许不同 SDK 与 GPU 平台接入，插件属性和真实行为仍需逐环境验证 |

拓扑保留在代码中，使条件分支与业务逻辑使用同一种语言，避免额外维护一套完整拓扑解释器。配置承担参数调整，块和原生图承担组合扩展。

新增能力时先判断机制与策略边界：通用生命周期、数据结构或构建能力进入框架，具体模型、业务规则与平台选择留在产品目录。任何扩展都应保留属性透传、无副作用预检和明确的验证边界。
